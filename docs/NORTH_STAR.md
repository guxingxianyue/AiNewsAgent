# AiNewsAgent 北极星规划

## 一句话定位

AiNewsAgent 是一个本地运行、面向技术读者的每日 AI 前沿情报 agent：每天从可信源中筛出真正值得读的 AI/CS 论文与趋势，用中文生成可解释、可追踪、可沉淀的简报。

它的目标不是替用户“看完所有新闻”，而是让用户在很短时间内知道：今天 AI 前沿有什么变化、为什么重要、我是否需要继续读原文或采取行动。

## 北极星目标

**让用户每天用 10 分钟以内，稳定获得 3-5 个对研发、产品判断或技术路线有行动价值的 AI 前沿洞察。**

这个目标强调三件事：

- **省时间**：用户不需要自己刷 arXiv、去重、筛标题、判断价值。
- **高信号**：入选内容必须和用户兴趣、技术深度、真实前沿变化相关。
- **可行动**：每条内容要说明“为什么重要”，并保留原始链接、评分、主题、标签和历史趋势，方便继续研究。

## 北极星指标

主指标：

**每日有效洞察数**

定义：一份每日简报中，被用户认为“值得继续读、收藏、分享、实验或影响决策”的条目数量。

阶段性目标：

- V0.1：每日报告稳定生成，至少 10 条候选中有 3 条明显有价值。
- V0.2：简报中 3-5 条内容能稳定命中用户长期兴趣。
- V0.3：系统能解释“为什么今天这些主题在变热”，并帮助用户回看历史脉络。
- V1.0：成为用户每天打开一次的 AI 研究雷达，而不是偶尔运行的脚本。

辅助指标：

- **生成稳定性**：定时任务每天成功产出简报的比例。
- **信号密度**：简报中“必读/值得扫读”条目的占比与用户回看率。
- **去重质量**：重复论文、同质化主题、低价值候选的出现次数。
- **解释质量**：入选理由是否具体，是否说明技术价值、潜在影响和适合读者。
- **趋势连续性**：同一主题在多日内是否能被正确聚合、展示和回溯。
- **本地可信度**：数据、配置、报告、运行历史都可在本地审计和迁移。

## 当前项目基线

AiNewsAgent 目前已经具备一个可工作的本地 agent 闭环：

- 从 arXiv 拉取最新 AI/CS 论文。
- 使用本地规则完成去重、关键词、分类和新鲜度粗排。
- 调用兼容 OpenAI 接口的 Mimo 模型进行重要性评分、主题归类、读者标注、标签和入选理由生成。
- 生成中文 Markdown 简报到 `reports/YYYY-MM-DD.md`。
- 使用 SQLite 保存运行历史、简报内容、入选条目、评分和失败原因。
- 提供 CLI：`init`、`doctor`、`preview`、`run-once`、`web`、`install-schedule`。
- 提供本地 Web 页面，支持查看今日/历史简报、候选条目、过滤搜索、运行历史和 7 天主题趋势。
- 支持 macOS LaunchAgent 每日定时运行。

这说明项目已经越过“能不能跑”的阶段，下一步重点应从功能堆叠转向“命中率、解释力、连续记忆和日常使用体验”。

## 产品原则

### 1. 少而准，胜过多而全

每天精选内容应控制在用户能读完的范围内。宁可漏掉边缘内容，也不要让简报退化成列表聚合。

### 2. 解释优先于摘要

标题和摘要只能回答“这是什么”，AiNewsAgent 必须进一步回答“为什么现在值得看”。入选理由、主题、重要性和适合读者是核心资产。

### 3. 趋势比单点更有价值

单篇论文的价值有限，连续多日出现的主题变化才更接近情报。系统应逐步从“每日精选”升级到“趋势雷达”。

### 4. 本地优先，可审计

项目应保持本地运行、本地存储、本地配置的特性。用户应该能知道数据来自哪里、模型如何参与、报告如何生成。

### 5. 可替换，不锁死

当前默认使用 Mimo 兼容接口，但架构应保留替换模型、增加来源、调整评分策略的空间。

## 目标用户

核心用户：

- 关注 AI 前沿的工程师、研究员、产品技术负责人。
- 需要快速了解 LLM、Agent、多模态、AI 编程、开源模型等方向变化的人。
- 希望拥有个人化、可本地持久化情报系统的人。

高价值使用场景：

- 每天早上快速阅读 AI 论文精选。
- 做技术选型前回看某个主题最近一周或一个月的变化。
- 为团队周会、研究分享、产品判断准备素材。
- 跟踪某些方向是否开始形成趋势，而不是只看单篇爆款。

暂不优先服务：

- 泛科技新闻阅读。
- 财经、营销、投资情绪追踪。
- 面向大众的娱乐化 AI 新闻。
- 追求实时推送的社交媒体热点监控。

## 战略路径

### 阶段 1：稳定可信的每日简报

目标：每天自动生成一份结构稳定、可解释、可回溯的 AI 前沿简报。

重点任务：

- 提升 `doctor` 对配置、网络、数据库、输出目录和模型响应格式的检查能力。
- 为 LLM 响应失败、JSON 解析失败、arXiv 失败建立更明确的降级策略。
- 在报告中固定展示数据来源、生成时间、失败警告和筛选口径。
- 为 `run-once` 增加更清晰的退出码和错误记录，方便定时任务诊断。
- 保持 CLI、Web 和数据库行为一致，避免同一能力在不同入口下表现不同。

验收标准：

- 无需人工干预即可连续 7 天生成报告。
- 失败时 Web 和运行历史能准确解释原因。
- 报告内容不因单个外部源失败而完全不可用。

### 阶段 2：提高信号命中率

目标：让精选结果越来越贴近用户真实兴趣，而不是只依赖固定关键词。

重点任务：

- 将用户兴趣从静态 `interests` 扩展为可演化的兴趣画像。
- 记录用户对条目的轻量反馈，例如收藏、隐藏、标记“有用/无用”。
- 将反馈用于后续排序，形成个性化权重。
- 拆分“研究价值”“工程可用性”“产品影响”“趋势信号”等评分维度。
- 优化去重逻辑，降低相似论文和同主题刷屏。

验收标准：

- 每日报告中至少 3 条内容被用户认为值得继续阅读。
- 用户隐藏过的低价值主题明显减少。
- 同一主题的多篇论文能被合并为趋势观察，而不是机械重复。

### 阶段 3：从日报升级为趋势雷达

目标：不只告诉用户今天有什么，还能告诉用户最近什么在持续升温、转向或衰退。

重点任务：

- 将主题趋势从 7 天词频升级为跨天主题簇。
- 为每个主题生成趋势说明：代表论文、变化方向、可能影响、推荐动作。
- 支持按主题查看历史条目和简报片段。
- 增加周报/月报生成能力，自动总结阶段性变化。
- 增加“观察清单”，允许用户长期跟踪特定主题。

验收标准：

- Web 首页能清楚展示近 7 天和近 30 天趋势。
- 用户能从一个趋势入口回溯到相关论文与历史简报。
- 周报能总结出 3-5 个连续变化，而不是简单拼接日报。

### 阶段 4：扩展高质量来源

目标：在不牺牲可信度的前提下，补充 arXiv 以外的信息源。

候选来源：

- Papers with Code：补充代码、数据集、SOTA 线索。
- GitHub Trending 或指定仓库：补充工程落地信号。
- Hugging Face：补充模型、数据集和 demo 生态信号。
- 会议与 workshop 页面：补充重要论文集和赛道变化。
- 用户自定义 RSS：补充个人关注源。

扩展原则：

- 新来源必须能提供稳定链接、发布时间和可解释文本。
- 每个来源都应有独立失败记录，不能拖垮整份简报。
- 来源扩展不能把系统变成“热点噪声聚合器”。

验收标准：

- 多来源内容在报告中有明确来源标识。
- 排序能区分论文价值、代码热度、模型发布和社区关注度。
- 新来源引入后，信号密度不下降。

### 阶段 5：形成个人知识资产

目标：让每天的简报不只是消费品，而是可搜索、可分析、可迁移的长期知识库。

重点任务：

- 提供更强的搜索：标题、摘要、主题、标签、作者、分类、日期范围。
- 支持导出 Markdown、CSV 或 SQLite 备份。
- 支持为条目添加个人备注。
- 支持按主题生成研究包：相关论文、趋势说明、原始链接、推荐阅读顺序。
- 为未来的本地向量检索或语义搜索预留接口。

验收标准：

- 用户可以快速找回过去某个主题的重要条目。
- 历史数据可以无损迁移到另一台机器。
- 系统能辅助准备技术分享或研究计划。

## 近期路线图

### 0-2 周：打磨可靠性

- 补强异常处理和错误落库。
- 增加 LLM 响应格式校验与可见警告。
- 让报告头部包含生成元信息。
- 增加关键路径测试：arXiv 失败、LLM 失败、空候选、重复运行。

### 2-4 周：打磨筛选质量

- 将评分拆成多维字段。
- 在 Web 中加入条目反馈入口。
- 将反馈保存到 SQLite。
- 在排序中引入反馈权重。

### 1-2 个月：打磨趋势能力

- 增加主题详情页。
- 增加周报生成命令。
- 将趋势从简单频次升级为主题簇。
- 支持按趋势回看历史材料。

### 2-3 个月：扩展来源

- 先接入一个高质量工程信号源，例如 GitHub 或 Hugging Face。
- 为 source 层定义统一接口和失败隔离策略。
- 在 Web 和报告中明确区分来源类型。

## 非目标

短期内不做：

- 不做泛新闻门户。
- 不做实时推送系统。
- 不做社交媒体情绪榜。
- 不做团队协作 SaaS。
- 不为了数量扩展低质量来源。
- 不把报告变成长篇百科式综述。

这些都可能有吸引力，但会稀释当前最重要的北极星：每天高信号、低负担、可行动的 AI 前沿洞察。

## 技术演进方向

推荐保持现有分层架构：

- `sources/`：外部信息源采集。
- `services/`：排序、LLM、报告生成等业务能力。
- `application/`：编排完整 pipeline。
- `infrastructure/`：配置、数据库、定时任务、环境初始化。
- `interfaces/`：CLI 与 Web 入口。

后续关键演进：

- 为 source 定义统一协议，降低新增来源成本。
- 将 LLM client 抽象为 provider，保留 Mimo 兼容接口作为默认实现。
- 将 scoring schema 显式版本化，避免未来数据难以迁移。
- 将报告模板与评分提示词独立管理，方便迭代评估。
- 在数据库中增加用户反馈、主题簇、来源状态和报告版本信息。

## 决策准则

当出现需求取舍时，按以下顺序判断：

1. 它是否提高每日有效洞察数？
2. 它是否减少用户判断成本？
3. 它是否提高系统稳定性或可解释性？
4. 它是否能沉淀为长期知识资产？
5. 它是否会引入过多噪声、维护成本或外部依赖？

如果一个功能不能服务前四项，或者明显伤害第五项，就应该延后。

## 成功画面

理想状态下，用户每天早上打开 AiNewsAgent，只需要几分钟就能看到：

- 今天最值得读的 AI 前沿论文。
- 每篇为什么重要，适合谁读。
- 哪些主题正在连续升温。
- 哪些内容值得进入自己的研究或产品判断。
- 所有原始来源和历史记录都能本地追溯。

这就是 AiNewsAgent 的北极星：**不是更多信息，而是更少噪声；不是替代判断，而是让判断更快、更稳、更有上下文。**
